## §2 Verification: each ask checked against current flowscope 0.12.0 source

### Plan 147 (`EveJsonWriter::write_anomaly_custom`) — confirmed needed

`EveJsonWriter::write_event<K>` ([`src/emit/eve.rs:write_event`](../../flowscope/src/emit/eve.rs)) only accepts `&FlowEvent<K>` and dispatches into private `write_anomaly` / `write_flow_ended` / `write_stats` based on the variant. The private `write_anomaly` takes `kind: &AnomalyKind` — the flowscope enum, **not** an arbitrary `&'static str` slug.

netring's `EveSink` adapter (Phase B.2) wants to emit anomalies whose `kind` is a netring detector slug like `"DnsQueryBurst"` or `"SshAttempt"` — strings that don't map to any `AnomalyKind` variant. Today the adapter has three bad options:

1. Wrap each emission in a synthetic `FlowEvent::FlowAnomaly { kind: AnomalyKind::Other(slug), … }` — but `AnomalyKind::Other` doesn't exist on the public enum.
2. Add a netring-side variant — wrong layer, blows up the AnomalyKind→metric-label mapping discipline that flowscope's `src/obs.rs` enforces.
3. Hand-roll EVE JSON in netring's `EveSink` — duplicates the entire schema (timestamp, flow_id, 5-tuple insertion, severity_numeric) that flowscope already maintains.

**Right answer:** ship a public `EveJsonWriter::write_anomaly_custom(...)` that takes (kind: &str, severity: Severity, ts: Timestamp, key: Option<&dyn KeyFields>, observations: &[(&str, &str)], metrics: &[(&str, f64)]) and emits a properly-shaped EVE anomaly event. The schema work stays upstream.

### Plan 148 (`Detector` trait) — confirmed needed

[`src/detect/patterns/mod.rs`](../../flowscope/src/detect/patterns/mod.rs) ships three detectors:
- `PortScanDetector` — returns `ScanScore` + `ScanVerdict`.
- `BeaconDetector` — returns `BeaconScore`.
- `DgaScorer` — returns `DgaScore`.

Each has a different feeding signature (TCP connection outcomes / flow-tuple inter-arrivals / DNS query strings), different score struct, and different lifetime semantics (some stateful per-key, some pure functions). No common trait.

netring 0.21 Phase I wants to wrap each in a `Detector<E, F>` via the `detector!` macro:

```rust
let port_scan = port_scan_detector! {
    name: "PortScanTRW",
    severity: Warning,
    detector: flowscope::detect::patterns::PortScanDetector::default(),
};
```

To write this macro **once** (not three times — one per pattern detector), netring needs a common trait. A trait that all three implement, with `name()`, `feed(input)`, `verdict()` methods. The exact shape needs care because the input types differ — see the detailed plan for the design.

### Plan 149 (`SlotHandle::drain_n`) — confirmed needed

[`src/driver/slot.rs:SlotHandle::drain`](../../flowscope/src/driver/slot.rs) loops `while let Some(msg) = self.inner.pop()`. The docstring is candid: *"Per-pop cost is ~10–15 ns on uncontended SegQueue; at the typical netring drain cadence (0–2 messages per `track_into` call) the difference vs a Vec batch-move is invisible. **Bulk drains with hundreds of pending messages will see the O(n) pop loop.**"*

netring 0.21 Phase C (sharded run loop) may drain less frequently than per-packet (e.g., once per N packets to amortize), and at load each drain could see hundreds of pending messages. The unbounded loop is a back-pressure hole — one shard's slow consumer can grow its SegQueue without bound.

**Right answer:** ship `SlotHandle::drain_n(out, max)` that pops at most `max` per call, returning the count. Consumers cap their batch size. SegQueue's `pop` is already lock-free; the new method is a 3-line variant of the existing loop with an extra counter.

### Plan 150 (`BroadcastSlotHandle`) — confirmed needed

[`src/driver/slot.rs:SlotHandle::Clone`](../../flowscope/src/driver/slot.rs) docstring: *"For broadcast (every consumer sees every message), drain into a channel and fan out yourself."*

This is exactly what netring 0.21 Phase F (`monitor.subscribe::<E>(...)`) needs to do. The "drain + channel + fan out" pattern reappears in every downstream that wants subscribe-style delivery. Built-in saves the boilerplate.

The MPMC SegQueue underlying `SlotHandle` doesn't support broadcast natively — broadcast needs per-consumer position tracking. Two implementations possible:
- (a) `BroadcastSlotHandle` backed by `tokio::sync::broadcast` (heavier; adds a tokio dep to flowscope — **rejected by the no-tokio rule**).
- (b) `BroadcastSlotHandle` backed by `Arc<Mutex<Vec<Subscriber>>>` where each `Subscriber` is a per-consumer `crossbeam_queue::SegQueue`. Push fans out, drain pops from one consumer's queue.

Option (b) is the right path. See the detailed plan.

### Plan 151 (`flowscope::OwnedAnomaly`) — confirmed shape

flowscope's emit writers each construct their own JSON/CSV/Zeek-shaped record from `FlowEvent::FlowAnomaly { key, kind, ts }`. Anomalies that carry netring-style labels + metrics (the `with("note", "v").with_metric("rtt", 432.5)` pattern) have no canonical owned shape upstream.

netring 0.21 ships `OwnedAnomaly` in `crate::anomaly::shipped_sinks`:

```rust
pub struct OwnedAnomaly {
    pub kind: &'static str,
    pub severity: Severity,
    pub ts: Timestamp,
    pub key: Option<String>,
    pub observations: Vec<(&'static str, String)>,
    pub metrics: Vec<(&'static str, f64)>,
}
```

Pushing this upstream to `flowscope::OwnedAnomaly` lets:
- `EveJsonWriter` accept it directly (no `FlowEvent` wrapper).
- `FlowEventNdjsonWriter` accept it directly.
- `ZeekConnLogWriter` skip it (Zeek conn.log is flow-shape, not anomaly-shape) — or emit as a `notice.log` row in a future PR.
- Downstream consumers (netring, sister crates) share one shape.

Schema lives next to `AnomalyKind` in flowscope. netring re-exports.

### Plan 152 (`PcapFlowSource::with_speed_factor`) — confirmed gap

[`src/pcap/mod.rs:PcapFlowSource`](../../flowscope/src/pcap/mod.rs) ships an iterator-based event source. Replay is **as-fast-as-possible** — no wall-clock pacing.

netring 0.21 Phase E (`MonitorBuilder::pcap_source`) + `run_until_idle` benefits from time-realistic replay for:
- Demo runs where the user wants live-cadence behavior.
- Training-data generation where the timing matters.
- Reproducing time-sensitive bugs (window-based detectors, RTT thresholds).

**Right answer:** ship `PcapFlowSource::with_speed_factor(f64)` (1.0 = real-time, 2.0 = 2× speed, `f64::INFINITY` = current behavior, the default). Plus `replay_at_wall_clock(start: SystemTime)` for offset replays.

### Plan 153 (`test_helpers::events`) — confirmed shape

flowscope's `src/test_helpers.rs` is gated on `test-helpers` feature for proptest / fuzz. It exposes `extract::parse::test_frames` — a frame builder, not event constructors.

netring's [`tests/monitor_dispatch_synthetic.rs`](../netring/tests/monitor_dispatch_synthetic.rs) and others manually construct `FlowStarted::<Tcp>::new(key, l4, ts)` using a `#[doc(hidden)] pub fn new` escape hatch on flowscope's typed events. Every downstream that drives the dispatcher synthetically rebuilds these helpers.

**Right answer:** ship a small `flowscope::test_helpers::events` module behind the existing `test-helpers` feature, with `started`, `ended`, `established`, `packet`, `tick`, `parser_closed`, `flow_anomaly`, `tracker_anomaly` constructors taking minimal-required-fields. Defaults the rest. Saves the `#[doc(hidden)]` escape hatch dance.

### Plan 154 (`FlowStateMap<T>`) — D1 from previous wishlist, now ready

The first wishlist (§D1) deferred per-flow `ctx.flow_state_mut::<T>()` until the KeyFields work landed. KeyFields is in. The design is now clear: `flowscope::tracker::FlowStateMap<T>` keyed by `FiveTupleKey`, with:
- `get_or_default(key)` / `get(key)` accessors.
- Auto-evict on `FlowEvent::Ended` for the key.
- Idle-timeout sweep matching `FlowTrackerConfig::idle_timeout`.

Lets netring expose `ctx.flow_state_mut::<T>()` (netring 0.21 §2.12) as a wrapper.

### Plan 155 (sharded-driver recipe) — confirmed gap

flowscope 0.12.0 made `SlotHandle: Send + Sync` and the CHANGELOG mentions sharded patterns. But there's no example or recipe doc showing the N-thread fanout shape. netring's Phase C plan reinvents this in its own docs.

**Right answer:** a small `examples/sharded_capture.rs` + `docs/recipes/sharded.md` showing the pattern. Mostly docs.

## §3 Plan 147 — `EveJsonWriter::write_anomaly_custom`: direct anomaly emission

### Summary

Add a public method to `EveJsonWriter` that emits an EVE `event_type: "anomaly"` record from caller-supplied (kind, severity, ts, key, observations, metrics) — bypassing the `FlowEvent::FlowAnomaly` wrapper. Lets consumers emit detector-named anomalies (`"PortScanTRW"`, `"DnsQueryBurst"`, `"BeaconCv"`) through the same EVE schema discipline as flowscope-internal anomalies.

### Status

Not started.

### Prerequisites

None. Self-contained in `src/emit/eve.rs`.

### Out of scope

- **Generalized `write_custom_*` for flow/stats event types.** The `write_event` shape already covers flow + stats; only anomalies need the custom-kind path because their `kind` field is a string slug (not a flowscope enum).
- **Severity transformation.** Caller supplies the final `Severity` enum value; the existing `EveOptions::severity_numeric` mapping function still applies on output.

### Files

| Action | Path | Purpose |

### API

## §4 Plan 148 — `Detector` trait unifying `PortScanDetector`/`BeaconDetector`/`DgaScorer`

### Summary

Introduce a small `Detector` trait that all three named-pattern detectors implement. Downstream consumers (netring's `detector!` macro, custom detection frameworks) get a single point of polymorphism: one wrapper macro adapts any detector to the host event-handler shape.

The trait is **deliberately minimal** — `name()`, `feed(input)`, `verdict()` — covering the union of what consumers do with the three detectors today. Specific score types stay separate (`ScanScore` ≠ `BeaconScore` ≠ `DgaScore`) because their shapes are genuinely different; the trait gives a common surface for *invocation*, not for *score interpretation*.

### Status

Not started.

### Prerequisites

None. Self-contained refactor of the three pattern modules.

### Out of scope

- **Cross-detector score normalization.** Scores remain detector-specific. Consumers that want a unified verdict roll their own threshold logic.
- **Mid-flight detector reconfiguration.** Detector state is owned by the caller; reconfiguration is dispose-and-reconstruct.

### Files

| Action | Path | Purpose |
|---|---|---|
| New | `src/detect/patterns/detector.rs` | `Detector` trait + supporting types |
| Modify | `src/detect/patterns/portscan.rs` | `impl Detector for PortScanDetector` |
| Modify | `src/detect/patterns/beacon.rs` | `impl Detector for BeaconDetector` |
| Modify | `src/detect/patterns/dga.rs` | `impl Detector for DgaScorer` |
| Modify | `src/detect/patterns/mod.rs` | `pub use detector::Detector;` |

### API

```rust
// src/detect/patterns/detector.rs
/// Common interface across the named-pattern detectors.
///
/// Each detector defines its own input event (`Input`) and score
/// type (`Score`); the trait gives a unified `feed` + `verdict`
/// shape so downstream frameworks (netring's `detector!` macro,
/// custom detection wrappers) can write one adapter that covers
/// all three.
pub trait Detector {
    /// Per-feed input — TCP connection outcome for `PortScanDetector`,
    /// (key, ts, bytes) tuple for `BeaconDetector`, query string slice
    /// for `DgaScorer`.
    type Input<'a>;

    /// Score produced by `verdict`. Concrete types: `ScanScore`,
    /// `BeaconScore`, `DgaScore`.
    type Score;

    /// Stable detector name suitable as an anomaly slug or
    /// metric label. Returns `"PortScanTRW"` /
    /// `"BeaconCv"` / `"DgaScorer"` for the shipped detectors.
    fn name(&self) -> &'static str;

    /// Feed one observation into the detector's per-key state.
    /// No return — verdict surfacing is via `verdict()`.
    fn feed<'a>(&mut self, input: Self::Input<'a>);

    /// Read the current verdict for a key (if the detector is
    /// per-key) or globally (if not). For pure-function detectors
    /// like `DgaScorer`, `feed` is a no-op and `verdict` accepts
    /// the input directly.
    fn verdict(&self, key: &dyn KeyFields) -> Option<Self::Score>;
}
```

Concrete implementations:

```rust
// portscan.rs
impl Detector for PortScanDetector<FiveTupleKey> {
    type Input<'a> = ConnectionOutcome;  // existing type
    type Score = ScanScore;
    fn name(&self) -> &'static str { "PortScanTRW" }
    fn feed(&mut self, outcome: ConnectionOutcome) { self.record(outcome) }  // existing
    fn verdict(&self, key: &dyn KeyFields) -> Option<ScanScore> {
        let src = key.src_ip()?;
        self.score_for(&src)  // existing
    }
}

// beacon.rs  → analogous, using (key_clone, ts, bytes_observed) as Input
// dga.rs     → feed is no-op; verdict accepts the input directly via Input
```

### Implementation steps

1. Define the `Detector` trait in `src/detect/patterns/detector.rs`.
2. Implement on each of the three existing pattern detectors. Each existing public method (`record`, `score_for`, etc.) stays as the underlying primitive — the trait methods delegate.
3. Update `docs/detect-patterns.md` with a "Using the `Detector` trait" section.
4. Tests: a generic `feed_then_verdict<D: Detector>` test that exercises all three implementations through the trait surface.

### Tests

- `detector_trait_invokes_portscan_correctly`.
- `detector_trait_invokes_beacon_correctly`.
- `detector_trait_invokes_dgascorer_correctly`.
- `detector_trait_name_is_stable_slug`.

### Acceptance criteria

- All three detectors compile through the trait.
- netring's `detector!` macro can have ONE pattern-detector adapter wrapper (not three) that lifts any `D: Detector` into a `Handler<E, _>`.
- New API additive — existing direct-call sites unchanged.

### Risks

- **R1: GAT for `Input<'a>`.** The lifetime parameter on `Input` requires GATs (stable since 1.65). Pre-1.65 toolchains break. **Mitigation:** flowscope's MSRV is already 1.75+ per CLAUDE.md — no concern.
- **R2: `Input` heterogeneity.** PortScan input is an enum; Beacon input is a tuple; DGA input is `&str`. The trait elegantly handles all three via the `Input<'a>` GAT, but consumers writing generic detector-using code need to thread the input type. **Mitigation:** document the per-detector input type prominently. The `detector!` macro hides it for netring users.

### Effort

- LOC delta: +200 (trait +50, three impls +120, docs + tests +30).
- Time estimate: **2 days**.

### Provenance

Triggered by netring 0.21 Phase I.1/I.2/I.3 — wanting one `detector!`-macro extension for all three shipped patterns instead of three separate wrappers.

## §5 Plan 149 — `SlotHandle::drain_n` + `swap_into`: bounded drain

### Summary

Add two methods to `SlotHandle<M, K>`:
- **`drain_n(out, max)`** — drain up to `max` messages. Bounded back-pressure for consumers under load.
- **`swap_into(out)`** — exchange the *entire* internal SegQueue with a caller-supplied empty queue. O(1) atomic-pointer swap, drains the whole batch in one move. Returns the consumer's previous queue (now empty) for reuse.

The existing `drain` stays as the convenience variant (unbounded loop). `drain_n` covers the common back-pressure case. `swap_into` covers the "consumer is faster than producer, just take everything" case at minimal cost.

### Status

Not started.

### Prerequisites

None.

### Out of scope

- **Reordering or filtering during drain.** Consumer post-processes.
- **Per-message ordering guarantees beyond SegQueue's FIFO-per-producer.** Same as today.

### Files

| Action | Path | Purpose |
|---|---|---|
| Modify | `src/driver/slot.rs` | Add `drain_n` + `swap_into` methods |
| Modify | `tests/driver_mt.rs` (or wherever the existing drain tests live) | Tests |
| Modify | `benches/zero_alloc.rs` | Bench addition for batch-drain comparison |

### API

```rust
impl<M, K> SlotHandle<M, K> where M: Send + 'static, K: Send + 'static {
    /// Drain at most `max` queued messages into `out`. Returns
    /// the number actually drained (may be 0 if the queue is
    /// empty or less than `max` if it had fewer).
    ///
    /// Bounded variant of [`drain`]. Use when:
    /// - Consumer wants explicit back-pressure (drop the rest
    ///   if downstream can't keep up).
    /// - Drain cadence is unpredictable (one shard's drain
    ///   shouldn't monopolize a CPU when another shard has
    ///   packets waiting).
    pub fn drain_n(&mut self, out: &mut Vec<SlotMessage<M, K>>, max: usize) -> usize {
        let mut n = 0;
        while n < max && let Some(msg) = self.inner.pop() {
            out.push(msg);
            n += 1;
        }
        n
    }

    /// Exchange the internal queue with a caller-supplied empty
    /// one. O(1) atomic swap — drains the entire pending batch
    /// in one move regardless of size.
    ///
    /// Returns the caller's input queue (now empty after the
    /// swap, available for reuse). The caller now owns the
    /// previously-pending messages in its own SegQueue, which
    /// it can iterate at leisure.
    ///
    /// Use when consumer wants the whole batch in one allocation-
    /// free move; cheaper than `drain_n(out, usize::MAX)` for
    /// dense bursts.
    pub fn swap_into(
        &mut self,
        replacement: Arc<SegQueue<SlotMessage<M, K>>>,
    ) -> Arc<SegQueue<SlotMessage<M, K>>> {
        std::mem::replace(&mut self.inner, replacement)
    }
}
```

### Implementation steps

1. Add `drain_n` — 5 lines.
2. Add `swap_into` — 2 lines. The user keeps their previous-now-empty queue in the returned `Arc` and can drain it themselves; their replacement becomes the slot's new buffer.
3. Tests for both methods.

## §6 Plan 150 — `BroadcastSlotHandle`: built-in fan-out semantics

### Summary

Ship a `BroadcastSlotHandle<M, K>` (sibling of `SlotHandle<M, K>`) where `Clone` produces a second consumer that sees **every** message — not a competitive consumer. Push fans out across all live subscribers.

Implementation: `Arc<BroadcastInner<M, K>>` where `BroadcastInner` holds a `Vec<Arc<SegQueue<SlotMessage<M, K>>>>` of per-subscriber queues (registered at clone time). Push iterates the subscriber list and pushes to each queue.

Trade-offs vs MPMC:
- One queue per subscriber instead of one shared queue.
- Push cost is O(subscribers).
- Drop semantics: when a subscriber is dropped, its queue is removed from the broadcast list — slow subscribers don't grow the producer's memory unboundedly.

### Status

Not started.

### Prerequisites

None.

### Out of scope

- **Latching the last message.** No "last value cache" for late subscribers.
- **Backpressure between subscribers.** Each subscriber's queue grows independently; a slow consumer's queue can grow unbounded. Cap externally via `SlotHandle::drain_n` (plan 149).
- **Cross-thread subscriber registration after first push.** Subscribers added before first push see all messages; subscribers added later see only messages from registration forward. Standard broadcast semantics.

| New | `src/driver/broadcast.rs` | `BroadcastSlotHandle<M, K>` + `BroadcastInner` |
| Modify | `src/driver/mod.rs` | `pub use broadcast::BroadcastSlotHandle;` |
| Modify | `src/driver/typed.rs` | `DriverBuilder::session_on_ports_broadcast` etc. (broadcast variants of the registration methods) |
| New | `tests/driver_broadcast.rs` | Cross-thread broadcast tests |

### API

```rust

use crossbeam_queue::SegQueue;

pub struct BroadcastSlotHandle<M, K>
where M: Send + 'static, K: Send + 'static {
    inner: Arc<BroadcastInner<M, K>>,
    /// This consumer's own queue inside the broadcast set.
    /// Removed from `inner.subscribers` on Drop.
    my_queue: Arc<SegQueue<SlotMessage<M, K>>>,
    parser_kind: &'static str,
}

struct BroadcastInner<M, K> {
    subscribers: Mutex<Vec<Weak<SegQueue<SlotMessage<M, K>>>>>,
}

impl<M, K> BroadcastSlotHandle<M, K>
where M: Send + Clone + 'static, K: Send + Clone + 'static {
    pub fn drain(&mut self, out: &mut Vec<SlotMessage<M, K>>) -> usize { … }
    pub fn drain_n(&mut self, out: &mut Vec<SlotMessage<M, K>>, max: usize) -> usize { … }
    pub fn pending(&self) -> usize { … }
    pub fn parser_kind(&self) -> &'static str { … }
}

impl<M, K> Clone for BroadcastSlotHandle<M, K>
where M: Send + 'static, K: Send + 'static {
    /// New consumer: gets its own queue inside the broadcast
    /// set. Subsequent pushes go to every live queue.
    fn clone(&self) -> Self {
        let my_queue = Arc::new(SegQueue::new());
        self.inner.subscribers.lock().unwrap().push(Arc::downgrade(&my_queue));
        Self { inner: Arc::clone(&self.inner), my_queue, parser_kind: self.parser_kind }
    }
}
```

## §11.5 Plan 156 — `Driver<E>::with_send_mode(mode)`: opt-in `Send` driver for tokio multi-thread

### Summary

Add a `SendMode` knob on `DriverBuilder<E>` that opts the built driver into a `Send + Sync` (or `Send + !Sync`) shape. Default stays `!Send` (current behavior — zero overhead). Opt-in users get a driver that survives `tokio::spawn` on the default multi-thread runtime.

Three implementations on offer, presented as **alternatives** for the maintainer to pick from. The user-visible API is the same regardless; the internal representation differs by mode.

This is a **P0** addition I omitted from the initial round-2 cut. The omission came from rolling forward flowscope 0.12.0's CHANGELOG language ("Driver<E> remains !Send") without re-examining whether the underlying constraint was structural or just "not yet asked for." netring's user-visible friction here is severe: every shipped example forces `#[tokio::main(flavor = "current_thread")]` or `LocalSet::run_until`. New users hit this on day one.

### Status

Not started.

### Prerequisites

None.

### Out of scope

- **Concurrent access from multiple threads.** Even in `Send + Sync` mode, all driver methods take `&mut self` — only one caller at a time. The `Sync` impl is decorative (lets the future be `Send`); actual mutation is single-owner.
- **Per-flow parallelism inside the driver.** Different flows still get processed serially within a driver. Multi-flow parallelism is netring-side (Phase F.3 per-CPU sharding).

### Why I dismissed this in the round-1 wishlist (and was wrong)

The first wishlist's §D2 said: *"Making `Driver<E>` Send would let users run the entire driver on a multi-thread runtime without `LocalSet`. Cost is much higher — every per-flow state mutation goes through a lock/queue. Defer until a consumer profiles and asks."*

That dismissal assumed the only path was `Arc<Mutex<HashMap<…>>>`. It isn't. For the tokio multi-thread use case, the actual requirement is **`Send` (movable across threads), not `Sync` (concurrently accessible)**. Tokio polls a future on one thread at a time; the executor moves the future across threads at await points but never accesses it concurrently. So `Send + !Sync` suffices, and that shape avoids per-mutation locking entirely.

### Design alternatives (maintainer picks one)

#### Alternative A — `Send + !Sync` via custom newtype (recommended)

Replace internal `Rc<RefCell<T>>` with a private `SendCell<T>` newtype:

```rust
pub(crate) struct SendCell<T>(Arc<UnsafeCell<T>>);

// SAFETY: SendCell is only constructed/dropped on the future's
// owning thread. Tokio's executor moves futures between threads
// at await points; no concurrent access can occur because the
// driver's methods take `&mut self`.
unsafe impl<T: Send> Send for SendCell<T> {}
// Explicitly NOT Sync — we never access from two threads at once.
```

**Cost: ~0%.** No locks. The unsafe is wrapped in a private type with the invariant clearly stated. The whole `Driver<E>` becomes `Send + !Sync`, which is **exactly enough** for tokio multi-thread:

```rust
#[tokio::main]  // multi-thread
async fn main() -> Result<()> {
    let handle = tokio::spawn(async move {
        Driver::builder(ext)
            .with_send_mode(SendMode::Tokio)
            .session_on_ports(HttpParser::default(), [80])
            .build()
            .track_into(view, &mut events);
    });
    handle.await?;
}
```

**Risk:** the `unsafe impl Send` must be defended in code. Document the invariant clearly: "single owner at a time; driver methods take `&mut self`." Audit the central tracker for any `&` (shared) leaks that would let two threads observe the inner state simultaneously. If any exists, the unsafe is wrong.

#### Alternative B — Sharded internal Mutex (~5–10% overhead at load)

Replace `HashMap<K, FlowEntry>` with a sharded structure: `Vec<Mutex<HashMap<K, FlowEntry>>>` of N shards (N = 16 or `num_cpus`). Each per-flow operation hashes the key to pick a shard, locks just that shard.

For low contention (different flows → different shards) the lock cost is ~10ns/op uncontended; at 1 Mpps that's ~1% CPU. Higher under contention (rare in practice).

**Cost: ~5–10% at high load.** Predictable, no unsafe.

**Risk:** more code change, longer rollout. Doesn't reuse the SegQueue work from plan 122.

#### Alternative C — `dashmap` for the central tracker (~3–8% overhead)

Same as B but using the `dashmap` crate (lock-striped HashMap) instead of hand-rolled shards. Drop-in for the central tracker's HashMap. Adds a public dep.

**Cost: ~3–8% at load.** Smaller code change.

**Risk:** new dep + dashmap's MSRV/API churn. dashmap has historically had subtle iteration-vs-mutation issues; flowscope's tracker iterates during sweep, which would need a careful audit.

### Recommendation

**Alternative A.** The `Send + !Sync` newtype path:
- Zero runtime overhead.
- Matches the actual tokio invariant (single-owner-at-a-time across threads).
- Minimal code change (replace the cell type, adjust trait bounds, add `unsafe impl Send`).
- Doesn't add a public dep.

The unsafe is small and auditable. The invariant is genuinely upheld by `&mut self` on every driver method.

### Files (assuming Alternative A)

| Action | Path | Purpose |
|---|---|---|
| New | `src/tracker/send_cell.rs` | Private `SendCell<T>` newtype with safety doc |
| Modify | `src/tracker/mod.rs` | Use `SendCell` instead of `Rc<RefCell>` for tracker-internal state when `SendMode::Tokio` |
| Modify | `src/driver/typed.rs` | `DriverBuilder::with_send_mode(mode)` |
| New | `src/driver/send_mode.rs` | `SendMode` enum |
| Modify | `tests/driver_tokio_send.rs` | Cross-thread future-move test (compile-time `Send` assertion + runtime test) |
| Modify | `docs/concepts.md` | Section on "Single-thread vs Tokio mode" |

### API (assuming Alternative A)

```rust
// src/driver/send_mode.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[non_exhaustive]
pub enum SendMode {
    /// Default. `Driver<E>` is `!Send` — uses `Rc<RefCell>` for
    /// the central tracker. Zero overhead; matches netring's
    /// single-thread runtime + `LocalSet` patterns and the pcap
    /// offline-replay path.
    SingleThread,

    /// `Driver<E>` is `Send + !Sync`. Uses a `SendCell` (private
    /// `Arc<UnsafeCell>` newtype). Zero overhead at runtime; the
    /// move-between-threads invariant is upheld by `&mut self`
    /// on every driver method.
    ///
    /// Use when running the driver inside a `tokio::spawn`-ed
    /// task on a multi-thread runtime. The driver itself never
    /// gets concurrently accessed; the runtime just moves it
    /// between worker threads at await points.
    Tokio,
}

impl<E: FlowExtractor> DriverBuilder<E> {
    /// Set the send-mode of the built driver. Default is
    /// [`SendMode::SingleThread`] for zero-overhead single-thread
    /// use; switch to [`SendMode::Tokio`] for multi-thread tokio
    /// runtimes.
    pub fn with_send_mode(self, mode: SendMode) -> Self { … }
}
```

### Implementation steps (Alternative A)

1. Implement `SendCell<T>` with `unsafe impl Send`, with a thorough safety comment that lists every invariant the impl relies on.
2. Audit `FlowTracker<E>` and `FlowDriver<E, R, M>` for any path that exposes `&` (shared, not exclusive) access to the inner state. Confirm every callsite goes through `&mut self`.
3. Add `SendMode` enum.
4. Add `DriverBuilder::with_send_mode`. Internally select between two tracker-state representations.
5. Add compile-time `Send` assertion: `const _: () = { fn assert_send<T: Send>() {} let _ = assert_send::<Driver<FiveTuple>>; };` gated to `SendMode::Tokio` configuration.
6. Runtime test: spawn a driver inside a `tokio::spawn`, drive it to completion across thread boundaries.
7. CHANGELOG: "Added `SendMode::Tokio` to `DriverBuilder`. Default unchanged. Drivers built with `SendMode::Tokio` are `Send + !Sync`, enabling `tokio::spawn`-ed driver tasks on multi-thread tokio runtimes."

### Tests

- `default_driver_is_not_send` (compile-fail test).
- `tokio_mode_driver_is_send` (compile-time assertion).
- `tokio_mode_driver_is_not_sync` (compile-fail test on `T: Sync`).
- `tokio_mode_driver_survives_tokio_spawn_on_multi_thread_runtime` (runtime test).
- `tokio_mode_driver_produces_identical_events_to_single_thread_mode` (correctness — same pcap, same events).

### Acceptance criteria

- Compile + test pass.
- Cross-thread tokio test passes on `#[tokio::main]` (multi-thread default).
- Bench: zero observable overhead vs `SendMode::SingleThread` on the existing `benches/zero_alloc.rs::driver_track_with_5_http_slots` workload.
- netring 0.21 can drop its `#[tokio::main(flavor = "current_thread")]` requirement from every example.
- Miri (`cargo +nightly miri test`) is clean on the SendCell path — important since we're adding unsafe.

### Risks

- **R1: unsafe impl Send invariant.** This is the central concern. The invariant is "no concurrent access from two threads at any point in time." Defenses:
  - The `Driver` only exposes `&mut self` methods. `&self` methods on `Driver<E>` would be a soundness break — verify none exist.
  - Any internal types stored alongside `SendCell` must also be `Send`. Audit the tracker's full field set.
  - Miri tests every PR that touches `SendCell` or the tracker.
  - Document the invariant on the type with a SAFETY block.

- **R2: future leakage of `&` access.** If a future flowscope feature adds an `&self` accessor (e.g., `tracker.snapshot() -> Snapshot`), the safety invariant breaks. **Mitigation:** mark the SendCell type with a comment forbidding new `&` accessors without re-auditing; add a clippy lint or doc-cfg check if possible.

- **R3: misuse via shared cloning.** If users `Arc::clone(&driver)` and try to use from two threads, the `!Sync` impl catches it at compile time. Confirmed safe.

- **R4: maintainer disagreement.** The flowscope project documents "stay runtime-free" and "single-thread by design" as principles. Opt-in Send mode preserves the runtime-free rule (no tokio dep added; `SendMode::Tokio` is a generic capability, not a tokio-specific knob) but bends the single-thread principle. The maintainer may prefer Alternative B or C, or push back on the whole ask.

### Effort

- LOC delta: +400 (SendCell ~100, tests ~200, docs + builder integration ~100). Alternative B would be +500–700.
- Time estimate: **3–4 days** for Alternative A including the Miri audit. Alternative B: 5–7 days. Alternative C: 2–3 days plus a dashmap dep audit.

### Provenance

netring 0.21 §2.4 marks `Monitor: !Send` as the most-felt friction by new users. The first wishlist downgrade ("not a roadblock anymore now that SlotHandle is Send") was wrong — `Monitor` owns the `Driver<E>` directly, and `Driver<E>: !Send` propagates. Every netring example today is forced into single-thread tokio. Multi-thread tokio is the *default* runtime; netring should not require users to opt out of it.

Per flowscope plan 120 audit, the allocation floor lives inside `simple-dns` / `tls-parser`. Rewriting those is a months-long effort with marginal payoff outside of 100 Gbps line-rate use cases. Defer.

Per flowscope's own 0.12 strategic review (`plans/INDEX.md:88-94`), all four were deferred for specific spec/dependency-maturity reasons. None bind netring 0.21.

### `BufferedReassembler::with_overflow_pageable`

Forensics-side feature (write overflow to disk). Per `plans/INDEX.md:126-129`, deferred — niche audience. No netring consumer.

### Wirefilter / nDPI FPC pattern

Per `plans/INDEX.md:153-159`, both deferred. No netring use case.

## §15 Open questions for the maintainer's LLM

These are the design forks I want feedback on before implementation lands.

### Q1 — Plan 147 `anomaly.type` policy

Default is `"applayer"` for the custom path. Should that be a `&'static str` constant (flexible — netring detectors can be any type) or a sealed enum (`AnomalyTypeStandard::Applayer | Stream | Decode`)? The sealed enum is stricter but blocks downstream-defined types.

**My recommendation:** `&'static str` constant in `EveOptions` (current proposal). Suricata's schema is open to new values; downstream tooling tolerates unknown `anomaly.type` strings.

### Q2 — Plan 148 `Detector::Input<'a>` GAT vs erased `&dyn Any`

GAT (current proposal) is type-safe but harder to compose generically. Alternative: `feed(&mut self, input: &dyn Any)` with internal downcast. Loses compile-time type safety.

**My recommendation:** GAT. flowscope's MSRV is 1.75+; downstream wrapper macros like netring's `detector!` thread the type without user friction.

### Q3 — Plan 149 `swap_into` API leakage

Exposing `Arc<SegQueue<…>>` in the signature ties the public API to the storage type. Alternative: opaque `SlotBuf<M, K>` newtype.

**My recommendation:** opaque newtype. Tightens the API.

### Q4 — Plan 150 broadcast subscriber Mutex

`Mutex<Vec<Weak>>` on every push works fine for low-frequency subscribe events but bottlenecks at high-frequency churn. Worth using `ArcSwap` from the `arc-swap` crate (lock-free) instead?

**My recommendation:** start with `Mutex<Vec<Weak>>`; instrument; switch to `ArcSwap` if profiling shows contention. Subscriber churn is rare in practice.

### Q5 — Plan 151 `OwnedAnomaly` Cow vs String

Cow is the right shape but adds 8 bytes per field. For dense anomaly streams (1M anomalies retained in memory) this is 16 MB overhead for 8 fields × 16 bytes = ouch.

**My recommendation:** Cow. Memory is rarely the binding constraint for retained anomalies (they're already an expensive shape — `Vec<observations>`); the flexibility wins.

### Q6 — Plan 154 `FlowStateMap` default tick cadence

Sweep frequency matters for memory bounds. Tie it to `FlowTrackerConfig::idle_timeout` directly? Or accept a separate `sweep_interval` knob?

**My recommendation:** tie to `idle_timeout` (one knob to set). Document explicitly that `sweep` is consumer-driven (call from your tick handler).

### Q7 — Plan 155 example: use core_affinity or skip it?

Pinning shards to specific CPUs is a real perf win but adds a `core_affinity = "0.8"` dev-dependency to the example. Worth it?

**My recommendation:** skip in the shipped example (simplest is best for didactic code); mention `core_affinity` in the recipe doc with a sample `Cargo.toml` for users who want it.

### Q8 — Plan 156 alternative choice: A (unsafe newtype), B (sharded Mutex), or C (dashmap)?

The biggest open question. My recommendation in the plan is A (zero overhead, small unsafe surface). But flowscope's safety posture may prefer C (no unsafe, ~3–8% cost, new dep). B is the middle.

**My recommendation:** A if the safety audit comes back clean (the unsafe surface is small and `&mut self`-bounded); C as the fallback. B only if dashmap's iteration semantics conflict with the tracker's sweep pattern.
