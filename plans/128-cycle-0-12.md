# Plan 128 — 0.12.0 cycle umbrella

## Summary

Umbrella plan for the 0.12.0 release. Five implementation
plans (122 / 123 / 124 / 126 / 127) consolidated from the
netring 0.21 wishlist + one "small wins" phase here.

Cycle theme: **add the Send-by-default slot handle, the
Suricata-compatible EVE emit, and the AnomalyFields /
Timestamp / correlate ergonomics that retire netring's
duplicated upstream code.**

Pre-1.0 break license used (`SlotHandle` becomes `Send + Sync`).
Other additions are behind opt-in features (`emit-eve`,
`chrono`) where they pull dependencies.

## Status

Not started. Plans 122 / 123 / 124 / 126 / 127 are queued.

## Prerequisites

- 0.11.1 published (✅ done).
- No outstanding 0.11 hot-fix work in flight.

## Out of scope

- **DNS / TLS decoder rewrite** — multi-day, no path to a
  patch. Revisit if a consumer profiles and asks.
- **Per-flow Ctx-state via `KeyIndexed`** — wishlist's D1.
  Defer to 0.13 (design needs more thought).
- **`Driver<E>` itself becoming `Send`** — wishlist's D2.
  Plan 122 ships handles as Send; the driver stays `!Send`
  (the central tracker's `Rc<RefCell>` internals would need
  a substantial rewrite).
- **Per-protocol EVE event types** (`eve_http`, `eve_dns`,
  `eve_tls`) — plan 123 ships lifecycle + anomaly only. Add a
  follow-up plan if a consumer asks.

## Consolidation decisions

The wishlist proposed 6 separate plans (122–127). After my
own review:

1. **Plan 122 consolidation**: collapsed the wishlist's
   feature-gated `MtSlotHandle` + parallel `MtDriverBuilder`
   into a single always-Send `SlotHandle`. Per-emit cost is
   negligible at netring's rates (~0.05% of a core at 1 Mpps
   × 10% L7); the simplification is significant (~400 fewer
   LoC, no feature flag, no parallel type system). Pre-1.0
   break: `!Send` → `Send` auto-trait transition.
2. **Plan 125 absorbed into 128 §Phase 7** — the three
   `correlate::*::new_unbounded` constructors are 5-line
   delegates. Don't earn a separate file; ship as a Phase 7
   small-wins section in this umbrella alongside the release
   mechanics.

Result: **5 plan files + 1 umbrella = 6 files**, down from
7 in the first draft.

## Phase 7 — `correlate::*::new_unbounded` small wins

Three trivial constructors that retire netring's duplicate
`correlate` module. Each is a 3-line delegate to the existing
`new` constructor with `usize::MAX` for capacity.

### Files

- `src/correlate/bucketed.rs` — `TimeBucketedCounter::new_unbounded(window, bucket)`
- `src/correlate/indexed.rs` — `KeyIndexed::new_unbounded(ttl)`
- `src/correlate/set.rs` — `TimeBucketedSet::new_unbounded(window, bucket)`

### API

```rust
// src/correlate/bucketed.rs
impl<K> TimeBucketedCounter<K>
where K: Hash + Eq + Clone
{
    /// Unbounded LRU capacity (`usize::MAX`). See [`Self::new`]
    /// for the bounded constructor — prefer it when memory
    /// pressure is a concern.
    ///
    /// Equivalent to `Self::new(window, bucket_width, usize::MAX)`.
    pub fn new_unbounded(window: Duration, bucket_width: Duration) -> Self {
        Self::new(window, bucket_width, usize::MAX)
    }
}

// src/correlate/indexed.rs
impl<K, V> KeyIndexed<K, V>
where K: Hash + Eq + Clone
{
    /// Unbounded capacity.
    pub fn new_unbounded(ttl: Duration) -> Self {
        Self::new(ttl, usize::MAX)
    }
}

// src/correlate/set.rs
impl<K, V> TimeBucketedSet<K, V>
where K: Hash + Eq + Clone, V: Hash + Eq + Clone
{
    /// Unbounded LRU capacity.
    pub fn new_unbounded(window: Duration, bucket_width: Duration) -> Self {
        Self::new(window, bucket_width, usize::MAX)
    }
}
```

### Implementation

1. Add the three constructors as 3-line delegates.
2. Cross-reference in rustdoc: `"see [Self::new_unbounded] to
   skip the capacity cap"`.
3. Regression tests: one per primitive showing `new_unbounded(…)`
   yields visibly identical behaviour to `new(…, usize::MAX)`.
4. CHANGELOG note under 0.12.0.

### Acceptance

- `cargo test --features tracker` passes the three new tests.
- Existing tests unchanged.
- netring 0.21 Phase G can write `flowscope::correlate::TimeBucketedCounter::new_unbounded(...)`
  directly.

### Effort

~¼ day. ~55 LoC.

### Notes

The wishlist listed 5 primitives. Trimmed to 3 —
`BurstDetector::new` has a different signature (no capacity
arg); `TopK::new(k)` is inherently bounded by `k`.

## Risks

- **Plan 122 SegQueue allocator pressure.** SegQueue grows by
  31-item blocks. If bench reveals push-rate > block-fill-rate
  in steady state, fall back to `ArrayQueue<N>` (bounded) +
  a per-slot capacity knob. Mitigation: existing bench
  harness catches this before release.
- **Plan 124 spec-materialisation closure complexity.** If the
  closure-based slot-spec approach gets tangled in HRTB
  inference, fall back to a per-kind spec enum (loses
  generic dispatch but composes cleaner).
- **Plan 123 (EVE) golden-fixture stability.** serde_json's
  default field ordering is unspecified. Mitigation: tests
  parse-back each line via `serde_json::Value` rather than
  byte-comparing.
- **Time budget pressure.** ~10 days estimate. Float ½ day
  buffer for inter-plan integration + the release dry-run.

## Provenance

Built from `flowscope-0.12-wishlist.md` (in repo root, retires
with the cycle). Plans 122–127 are my renderings of the
wishlist plans into flowscope's standard 12-section template,
with three substantive corrections / sharpenings:

- **Plan 122 (consolidated)**: wishlist proposed a feature-
  gated `mt` flag + parallel `MtSlotHandle` / `MtDriverBuilder`
  types. Consolidated to a single always-Send `SlotHandle`
  via `Arc<SegQueue>`. Per-emit cost (~5–10 ns extra) is
  negligible at netring's rates; the simplification (~400
  fewer LoC, no feature flag, no parallel builder) is
  significant. Pre-1.0 break: `!Send` → `Send`.
- **Plan 124**: wishlist proposed `Driver::deferred()` whose
  `build()` panics if no extractor was set. Sharpened: a
  distinct `DeferredDriverBuilder<E>` type that only exposes
  `build_with(ext)`. Compile-time guarantee preserved; no
  runtime regression.
- **Plan 126**: wishlist's `AnomalyKind` mapping referenced
  variants that don't exist in shipped flowscope
  (`SegmentOutOfWindow`, `TcpRstAfterFin`, etc.). Corrected
  to the 6 actual variants.
- **Plan 127**: wishlist's "½ day" effort estimate undercounts
  the hand-rolled date algorithm + cross-check tests against
  chrono. Realistic: ~1 day.
- **Plan 125 absorbed**: 3 trivial ctors don't earn a separate
  plan file. Folded into Phase 7 here.
